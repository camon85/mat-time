# Mat Time — 구현 문서 🔧

앱을 고치거나 왜 이렇게 만들었는지 궁금한 사람을 위한 문서.
그냥 쓰기만 할 거라면 [`../README.md`](../README.md) 로 가세요 — 여긴 재미없습니다.

여기부터는 "왜"를 남기는 게 목적이라 건조합니다. 대부분의 항목에는
그렇게 만들 수밖에 없었던 사고나 측정이 하나씩 붙어 있어요.

주짓수 출석 트래커. 체육관 승급 최소 기준(수련 기간 + 출석 일수)에 대한 진행도를 추적하는 정적 웹앱.
서버·빌드·의존성이 없다. 마크업 한 장, 스타일시트 한 장, 일반 스크립트 다섯 장이 전부이고,
서비스 워커가 그 파일들을 캐시해 오프라인에서도 열린다 (§파일 구성).

## 승급 추적은 옵션이다 (기본 꺼짐)

**승급 이력을 남기는 것과 다음 승급을 예측하는 것은 다른 일이다.**

- 이력 = "지금 내 벨트가 무엇인가". 어느 체육관에서나 사실이고, 항상 켜져 있다
- 추적 = "다음 승급까지 얼마나 남았나". **한 체육관의 규정**(아래 표, 그리고 매월 마지막
  금요일 승급식)에 기대므로, 규정이 다른 곳에서는 그냥 틀린 숫자다

그래서 `state.trackPromotion` 으로 나누고 **기본을 꺼짐**으로 둔다.

**이력이 있는지로 추론하지 않는다.** "승급 이력을 넣었으니 진행도도 보고 싶겠지"는 성립하지
않는 추론이다 — 벨트를 맞추려고 이력을 넣은 사람이 남의 체육관 기준 D-day 까지 원한 건 아니다.
설정값이 없으면 이력이 있든 없든 꺼짐이다.

| 켜야 보이는 것 | 항상 보이는 것 |
|---|---|
| 승급 진행도 카드 (기간·출석 진행률, 예상 승급식) | 헤더의 벨트와 승급일 |
| 블랙까지 로드맵 | 달력의 승급일 주황 점 |
| 달력의 승급식(마지막 금요일) 테두리와 그 범례 | 잔디의 승급 노란 칸 |
| | 설정의 승급 이력 목록·기록 폼 |
| | 출석 통계 전부 (총 출석·연속·페이스·잔디) |

**끄는 것은 감추는 것이지 지우는 것이 아니다.** 이력·출석·메모는 그대로 남고, 다시 켜면
그동안의 기록으로 즉시 계산된다 — 되살릴 것이 없다. 자세한 결정 과정은
[`decisions/DR-006`](decisions/DR-006-optional-promotion-tracking.md).

## 승급 최소 기준

| 구간 | 수련 기간 | 출석 일수 |
|---|---|---|
| 화이트 0그랄 → 4그랄 (4단계) | 3개월 | 30일 |
| 화이트 4그랄 → 블루, 이후 블랙까지 전 단계 (16단계) | 7개월 | 90일 |

두 조건을 **모두** 충족해야 하므로 종합 진행률은 둘 중 낮은 쪽으로 표시한다.
화이트 0그랄부터 블랙벨트까지 총 20단계. (추적을 켠 경우에만 계산·표시한다)

**승급식은 매월 마지막 금요일**이다. 기준을 채운 날 바로 승급하는 게 아니라
그 뒤 처음 오는 승급식에 올라간다. 앱은 목표 승급식 날짜와 D-day 를 함께 보여준다.

새 단계의 출석은 **승급식 다음 날부터** 센다. 승급식 당일 수련은 이전 단계의 마지막 출석으로 본다.

## 기능

- 출석 체크 — 달력에서 날짜를 탭. 오늘·지난 날짜 모두 같은 방식이고 다시 누르면 취소
  (취소에는 토스트 되돌리기가 붙는다). 미래 날짜와 이웃 달 칸은 누를 수 없다
- 다음 승급까지 진행도 — 기간 / 출석 일수 각각 + 종합, 목표 승급식과 페이스 기반 예상일
- 블랙벨트까지 전체 로드맵 (벨트 그래픽)
- 승급 기록 — 현재 벨트·단계 시작일이 여기서 파생 (과거 출석 기록은 보존)
- 주짓수 시작일 기록 → 총 수련 기간 표시 (옵셔널)
- 기록 카드 — 총 출석 / 연속 주 / 최근 4주 페이스, 지난달 대비, 최근 1년 출석 잔디
- 날짜별 메모 — 출석과 **독립**. 분류(추가·삭제 가능, 최대 10개) + 검색 (옵셔널)
- JSON 백업 / 복원(형식 검증 포함), 깃허브 Gist 동기화 (옵셔널)

## 승급 기록 = 현재 상태

**현재 벨트·그랄과 단계 시작일을 따로 설정하는 곳은 없다.** 승급 이력의 가장 최근 항목이
곧 지금 상태이고, 그 날짜부터 다음 승급 기준을 센다 — 승급일과 단계 시작일은 같은 사실이다.

설정 → 승급 이력 → **＋ 승급 기록** 에서 `승급일` · `받은 벨트` · `받은 그랄` 을 넣는다.
기본값은 **오늘 + 다음 그랄**이라, 오늘 받았으면 열어서 바로 기록하면 된다.
처음 쓸 때는 마지막으로 승급한 날을 기록하면 현재 벨트가 맞춰진다.

벨트는 셀렉트가 아니라 **벨트 그래픽을 눌러서** 고른다. 고른 칩은 선택한 그랄까지 함께
그려지므로 결과 미리보기가 따로 필요 없다. 화이트는 1그랄부터, 블랙은 그랄 행 자체가 숨는다.
벨트를 화이트로 바꾸면 0그랄이 자동으로 1그랄로 보정된다.

- 이력이 비어 있으면 화이트 0그랄로 보고, 기준일은 주짓수 시작일(없으면 오늘).
  이때 헤더는 날짜 대신 `수련 N일째` 만 보여준다 — 날짜는 「기록」 카드와 중복이기 때문
- **화이트 0그랄은 승급 대상이 아니다.** 시작 상태이므로 그랄 선택지에서 뺐다
- 미래 날짜는 폼에서 선택할 수 없다 (백업 파일을 직접 고쳐 넣으면 「승급 예정」으로 표시된다)
- 같은 날짜를 다시 기록하면 기존 항목을 교체한다 (확인 후)
- **같은 등급은 두 번 기록할 수 없다.** 같은 벨트·그랄이 다른 날짜에 이미 있으면
  새로 쌓지 않고 「승급일을 옮길까요?」를 묻는다. 폼에서도 누르기 전에 미리 알려준다
- 기록한 날짜는 캘린더에 주황색 점으로 표시된다
- 항목을 **삭제**하면 자동으로 직전 상태로 돌아간다. 되돌리기 버튼이 따로 없는 이유다
- 출석 기록은 어느 경우에도 지워지지 않는다

## 주짓수 시작일

설정의 유일한 직접 입력 텍스트값. 처음 도장에 등록한 날이며 「기록」 카드에 `6년 5개월째` 로
표시된다. **승급 계산에는 쓰이지 않고**, 비워 둬도 된다.

동기화 시 이 값만은 "최신 우선"이 아니라 **더 이른 날짜**를 채택한다.
시작일은 가장 이른 기록이 진실이므로, 한쪽 기기에만 입력해도 지워지지 않는다.

위 주소를 폰 브라우저로 연 뒤

## 설치와 오프라인

이 앱은 **지하 체육관·지하철·비행기에서 여는 앱**이다. 기록은 localStorage 에 있으니
네트워크와 무관할 것 같지만, 정작 **앱 껍데기를 못 받아와 화면 자체가 안 떴다.**

### 서비스 워커 — stale-while-revalidate

`sw.js` 가 앱 셸(HTML·CSS·스크립트 5개·아이콘)을 캐시한다. 전략은 하나다.

- 캐시에 있으면 **즉시** 준다 (네트워크를 기다리지 않아 실행이 항상 빠르다)
- 동시에 뒤에서 받아 캐시를 갱신한다 → 다음 실행부터 최신 코드
- 없으면 네트워크, 그것도 실패하면 내비게이션을 `index.html` 로 되돌린다

셋 중에 이걸 고른 이유:

| 전략 | 문제 |
|---|---|
| network-first | 새 코드를 즉시 받지만 **느린 회선에서 매번 기다린다** |
| cache-first (버전 수동) | 빠르지만 **버전을 올리는 걸 잊으면 영영 옛 코드가 남는다** |
| **stale-while-revalidate** | 갱신이 한 번 늦다. 대신 잊을 것이 없다 |

이 프로젝트의 배포는 「파일을 푸시」 하나뿐이라 **손으로 버전을 올리는 것을 잊는 쪽**이
더 위험하다. 코드 반영이 한 번 늦는 것은 하루 한 번 여는 앱에서 사실상 즉시다.

주의할 것 둘.

- **`api.github.com` 은 절대 캐시하지 않는다.** 같은 출처만 다루므로 자연히 걸러지지만,
  캐시했다면 동기화가 옛 Gist 를 읽고 그걸로 병합해 기록을 되돌렸을 것이다
- **200 이 아닌 응답은 캐시에 넣지 않는다.** 넣으면 깨진 파일이 그대로 고착된다

`file://` 에서는 등록 자체가 막히므로 `location.protocol` 을 먼저 본다 — 파일을 더블클릭해
확인하는 개발 흐름이 깨지지 않아야 한다.

### 상단 안전영역 — 홈 화면에서만 드러나는 문제

`apple-mobile-web-app-status-bar-style: black-translucent` + `viewport-fit=cover` 는
**내용을 상태바 아래까지** 그린다. 여백을 주지 않으면 맨 위 벨트가 시계·노치에 통째로 가린다
(실측: 안전영역 59px, 벨트 상단 26px). **브라우저 탭에서는 보이지 않고 홈 화면 실행에서만**
나타나므로 오래 눈에 띄지 않았다.

`env(safe-area-inset-top)` 으로 세 곳을 맞춘다.

| 곳 | 처리 |
|---|---|
| `.wrap` | `padding-top: calc(20px + env(safe-area-inset-top))` |
| `body::before` | 그 높이만큼 앱 배경을 **깔아 둔다** — 안 깔면 스크롤한 글자가 시계 옆을 지나간다 |
| `.page-top` | `top: env(safe-area-inset-top)` — 「전체 메모」 고정 바가 상태바 아래에 붙게 |

**JS 도 같은 값을 알아야 한다.** 월 머리글은 고정 바 *아래*에 이어 붙고(`--notes-stick`),
연·월 점프는 그 지점으로 스크롤한다. 둘 다 예전엔 `.page-top` 의 **높이**만 썼는데, 이제는
그 위에 얹힌 안전영역까지 더해야 한 줄도 안 어긋난다 → `notes.js :: stickOffset`.

`env()` 는 안전영역이 없는 곳에서 0 이므로 브라우저 탭·안드로이드·데스크톱에서는
아무 일도 일어나지 않는다. **iOS 버전마다 상태바를 어떻게 잡는지 따질 필요가 없는 것이
이 방식의 값이다.**

좌우는 손대지 않았다. 가로 화면은 폭이 넉넉해 `max-width: 520px` 가운데 정렬만으로
노치보다 훨씬 큰 여백이 생긴다.

> 크로미움의 `Emulation.setSafeAreaInsetsOverride` 로 아이폰 값을 넣어 검증한다
> (`dev/smoke.py` — 「안전영역」 절). 없는 버전에서는 그 절만 건너뛴다.

### manifest 와 아이콘

**둘은 플랫폼이 다르다.**

| | 안드로이드 크롬 | iOS 사파리 |
|---|---|---|
| 설치를 가능하게 하는 것 | **`manifest.webmanifest`** | `apple-mobile-web-app-capable` (원래부터 있었다) |
| 홈 화면 아이콘 출처 | 매니페스트 `icons` | **`apple-touch-icon`** (매니페스트는 뒷순위) |
| 설치 유도 | 크롬이 배너를 띄운다 | **없다** — 공유 → 홈 화면에 추가를 직접 |
| 없을 때 | 주소창 달린 **북마크 바로가기** | 아이콘이 **페이지 스크린샷**이 된다 |

즉 매니페스트가 실제로 바꾼 것은 **안드로이드의 설치 경험**이고, iOS 에서 달라진 것은
`apple-touch-icon` 하나다 — 매일 열라고 안내하면서 홈 화면에 얼룩을 남기고 있었다.

아이콘은 `dev/gen-icons.py` 가 그린다 (앱 화면의 벨트 그래픽을 그대로 옮긴다).
결과 PNG 는 커밋되므로 **앱과 배포에는 여전히 의존성이 0** 이다.
32px 에서는 그랄 넷이 한 덩어리로 뭉개져 둘만 그린다. maskable 아이콘은 OS 가 잘라내므로
벨트를 안쪽 55% 안에 담는다.

## 데이터 저장 위치

기본은 브라우저 **localStorage**. 키가 둘이다 — `bjj-attendance`(출석·승급·설정)와
`bjj-notes`(메모). 나눈 이유는 [메모](#메모) 절 참조. 어느 쪽이든 다음을 뜻한다.

- 데이터는 **그 기기의 그 브라우저에만** 있다. 서버로 전송되지 않는다.
- 기기·브라우저를 바꾸면 기록이 따라오지 않는다.
- 브라우저 데이터 삭제, 시크릿 모드 종료 시 사라진다.
- iOS Safari 는 7일 이상 방문하지 않은 사이트의 저장 데이터를 자동 삭제할 수 있다
  (홈 화면에 추가해 두면 이 정책에서 제외된다).

대응책은 두 가지다. 아래 **동기화**를 켜거나, **설정 → 백업(JSON)** 으로 파일을 받아 두는 것.

### 읽지 못한 데이터는 덮어쓰지 않는다

예전에는 `load()` 가 「없음」과 「손상」을 똑같이 `false` 로 돌려줬고, 호출부가 곧바로
`save()` 로 기본값을 써서 **읽지 못한 원본이 그 자리에서 사라졌다.** 동기화를 안 켠
사용자에게는 그게 곧 전체 유실이다.

지금은 `"ok" | "empty" | "corrupt"` 를 구분한다. 손상이면 원본을 `bjj-attendance-corrupt` 로
옮기고(지우지 않는다) 사용자에게 알린다. 부팅 직후 알림을 띄우면 첫 렌더와 겹치므로 조금 미룬다.

### 자정을 넘기면 다시 그린다

`render()` 는 사용자 조작과 앱 복귀 때만 돈다. 켜 둔 채 자정을 넘기면 「오늘」 테두리가 어제에
남아 **엉뚱한 날짜를 누르게 된다.** 데스크톱에서 탭을 띄워 두는 흐름에서 잘 걸린다.
다음 자정 +5초에 `render()` 하고 다시 예약한다. 절전에서 깨면 타이머가 밀려 있을 수 있어
`visibilitychange` 에서도 다시 건다.

## 기기 간 동기화 (GitHub Gist)

서버 없이 기록을 여러 기기에서 공유하는 선택 기능이다. 켜지 않아도 앱은 그대로 동작한다.

### 원리

깃허브 개인 토큰으로 브라우저가 **비공개 Gist** 하나를 직접 읽고 쓴다.
중간 서버가 없고, 기록은 본인 깃허브 계정에만 저장된다.

### 설정

1. 설정 패널의 **토큰 발급 →** 링크를 연다 (`gist` 권한만 체크된 상태로 열린다)
2. 만료 기간을 고르고 토큰 생성 → 값 복사
3. 앱의 **깃허브 토큰** 칸에 붙여넣고 **연결**

Gist 는 자동 생성된다. 다른 기기에서 같은 토큰을 넣으면 그 Gist 를 찾아 기록을 이어받는다.

### 동기화 시점

- 출석 체크·설정 변경 후 1.5초 (디바운스)
- 앱을 열거나 다시 활성화할 때
- **지금 동기화** 버튼

### 병합 규칙

| 항목 | 규칙 |
|---|---|
| 출석 날짜 | 날짜마다 **켠 시각(`checked`) vs 끈 시각**을 비교해 늦은 쪽 — 추가도 취소도 전파된다 |
| 승급 이력 | 출석과 **같은 규칙**, 켠 시각은 항목의 `at` — 삭제도 전파된다 |
| 메모 | 날짜의 생사는 같은 규칙, **본문은 메모마다 가진 저장 시각(`at`)** 으로 판정 |
| 분류 | 같은 규칙, 켠 시각은 항목의 `at` |
| 주짓수 시작일 | 더 이른 날짜 |
| 초기화 · 복원 | 병합하지 않고 Gist 를 **덮어쓰고 세대(`epoch`)를 올린다** |

**"켠 시각"은 반드시 항목마다 가져야 한다.** 한때는 문서의 `updatedAt` 으로 대신했는데,
그러면 그 기기가 무엇이든 고칠 때 살아 있는 모든 항목의 주장 시각이 함께 밀려 상대의
툼스톤을 통째로 이긴다 — 「폰에서 지우고 나중에 PC 를 열어 오늘 체크」에서 지운 출석이
되살아났다. 자세한 경위는 [`lessons-learned.md`](lessons-learned.md) M7-1,
결정 과정은 [`decisions/DR-001`](decisions/DR-001-per-item-sync-stamps.md) 참조.

Gist 안에 파일이 둘이다 (`bjj-attendance.json` · `bjj-notes.json`). 각각 따로 병합하고
**달라진 파일만 올린다** — 출석만 체크하면 메모 파일은 건드리지 않는다.

세대를 올리는 이유는 덮어쓰기만으로는 부족해서다. 다른 기기가 옛 데이터를 든 채 동기화하면
지운 것이 전부 되살아나는데, 세대가 낮은 문서는 병합 없이 버려지므로 그 일이 막힌다.

복원은 덮어쓰기이므로 파일 형식을 먼저 검사한다. **항목 하나라도 어긋나면 파일 전체를 거부**하고
기존 기록은 그대로 둔다 — 일부만 걸러 받으면 무엇이 사라졌는지 알 수 없기 때문이다.
통과하면 무엇이 들어오는지(출석 N일 · 이력 N건) 보여준 뒤 확인을 받는다.
자세한 검사 항목은 [`data-format.md`](data-format.md) §9.1 참조.

취소한 날짜는 취소 시각과 함께 남겨 두기 때문에 다른 기기로도 삭제가 전파된다.
자세한 규칙은 [`data-format.md`](data-format.md) §7 참조.

### 동기화는 한 번에 하나

트리거가 넷이다 — 변경 후 1.5초 디바운스 · 앱 복귀 · 「지금 동기화」 · 부팅. 겹치면 두 실행이
같은 원격을 읽고 각자 PATCH 해서 나중에 도착한 쪽이 먼저 것을 지운다. 로컬은 온전하므로 다음
동기화에서 회복되지만 그때까지 Gist 가 뒤처진다. 돌고 있으면 요청을 버리지 않고 **끝난 뒤
한 번 더** 돌린다 (`syncing` / `syncAgain`) — 그냥 버리면 마지막 변경이 안 올라간다.

### Gist 탐색은 페이지를 넘긴다

`/gists` 한 페이지(100개)만 보면 gist 가 많은 계정에서 기존 기록을 놓치고 **새 gist 를 만든다.**
사용자 눈에는 「다른 기기 기록이 안 따라온다」로 보인다. 찾을 때까지 최대 10페이지를 넘긴다.

### 토큰 취급

- 토큰은 `bjj-attendance-sync` 키에 **기록과 분리**해 저장되며, JSON 백업 파일에 포함되지 않는다
- `gist` 권한만 있으므로 유출되어도 저장소·계정 설정에는 접근할 수 없다
- 공용 PC 에서는 쓰지 말고, 필요하면 **연결 해제** 또는 깃허브에서 토큰을 폐기한다
- 비공개(secret) Gist 는 검색에 노출되지 않지만 URL 을 아는 사람은 볼 수 있다 — 완전한 비공개는 아니다

## 메모

출석은 "갔다/안 갔다" 만 말한다. 그런데 남기고 싶은 건 그것만이 아니다 — 세미나에서 들은 말,
대회 결과, 본 영상, 수업에서 배운 기술, 혼자 깨달은 것.

### 출석과 왜 독립인가

출석 체크로 대신할 수 없다. **대회에 나간 날은 도장에 안 간 날이고, 영상은 매트를 밟지 않고 본다.**
그래서 메모를 써도 출석이 켜지지 않고, 출석을 취소해도 메모는 남는다.
메모 팝업에 "출석도 함께 체크" 같은 편의 옵션을 두지 않은 것도 같은 이유다 —
둘을 엮는 순간 이 기능의 전제가 무너진다.

### 저장을 문서 둘로 나눈 이유

`bjj-attendance` 와 `bjj-notes` 를 따로 둔다. Gist 도 같은 gist 안의 두 파일이다.

메모는 코어의 10~30배 크기가 된다 (실측: 10년 뒤 코어 28 KB vs 메모 315 KB,
[`data-format.md` §11.1](data-format.md#111-메모-문서--왜-따로-두는지가-여기-있다)).
한 문서에 뒀다면

- **출석을 한 번 탭할 때마다** 메모 전체를 직렬화해 쓰고 Gist 에 업로드했을 것이다
- `setItem` 은 호출 하나라, 메모가 커져 저장이 실패하면 **출석까지 같이 못 쓴다**
- 코어가 Gist 의 1 MB inline 임계를 넘어 매번 `raw_url` 로 우회하게 될 수 있다

주의할 오해 하나 — **localStorage 할당량은 오리진 단위라 키를 나눠도 총량은 늘지 않는다.**
분리가 버는 것은 용량이 아니라 *실패의 격리*와 *쓰기 크기*다.

나누는 비용은 **지금이 0** 이라서 지금 했다. `bjj-notes` 키가 없으면 빈 문서로 시작하고,
Gist 에 `bjj-notes.json` 이 없으면 다음 PATCH 때 만든다. gist 탐색 기준은 여전히
`bjj-attendance.json` 이라 메모 도입 이전 gist 도 그대로 찾는다. 마이그레이션 코드가 한 줄도 없다.
데이터가 쌓인 뒤였다면 기기마다 형식이 다른 상태를 넘겨야 했다.

백업 파일은 **계속 하나다.** 두 문서를 이어 붙인 평평한 객체라 사용자 입장에서 달라진 게 없고,
검증(`validateBackup`)도 함수 하나로 끝난다.

### 메모마다 저장 시각(`at`)을 갖는 이유

출석·승급은 켜짐/꺼짐이라 문서의 `updatedAt` 을 "켠 시각" 대용으로 써도 충분했다.
그러나 **메모는 내용이 바뀐다.** 문서 단위 시각만으로는 어느 기기의 어느 메모가 최신인지
가릴 수 없다 — A 가 3/1 에 메모 X, 3/5 에 메모 Y 를 고치면 A 의 `updatedAt` 은 둘 다 3/5 가 되어
B 가 3/2 에 고친 X 가 부당하게 밀린다.

병합에서 날짜의 생사는 출석과 같은 툼스톤 규칙, 본문만 `at` 으로 가린다.
승급 이력이 쓰는 "뒤에 넣은 쪽이 이기는 Map" 을 그대로 쓰면 안 된다 —
이력은 날짜가 곧 사실이라 양쪽 내용이 같지만, 메모는 본문이 다르다.

### 하루에 하나

날짜가 곧 키다. 여러 개 쓰고 싶으면 줄바꿈으로 적는다.
이 제약 덕에 병합이 "날짜마다 늦은 쪽" 한 줄로 끝나고, 출석·승급 이력과 같은 툼스톤 구조를
그대로 재사용할 수 있다. 항목마다 id 를 발급하고 정렬 순서를 병합하는 문제가 사라진다.

### 쓰기와 읽기를 한 카드에

- **쓰기** — 달력 헤더의 연필 아이콘 → 팝업. 오늘 날짜가 기본값이라 체크 직후 바로 적을 수 있다
- **그날에 바로 쓰기** — 달력 칸을 **길게 누르면** 그 날짜로 열린다 (아래 「달력」 절)
- **읽기** — 달력 격자 아래 「이 달의 메모」. 최대 3개 + `N개 더`
- **찾기** — 「전체 메모 →」 **화면**. 분류 칩 + 검색 + 전체 목록 (아래 절)

**목록을 달력에 붙인 이유**는 메모가 날짜 데이터이기 때문이다. 달력 칸의 `—` 표식과 바로 아래
목록이 같은 것을 가리키고, 월을 넘기면 목록도 따라간다 — 월 이동이 곧 메모 탐색이 된다.

연필은 **두 곳**에 있다 — 달력 헤더와 전체 메모 화면 헤더. 같은 아이콘·같은 자리라
따로 배울 게 없고, 서로 다른 화면에서 같은 동작을 여는 것이라 중복이 아니다.
전체 메모를 보다가 하나 더 쓰려고 화면을 나갔다 오는 게 더 어색하다.

**높이** — 목록은 격자 *아래*라 달력 칸과 이동 버튼은 달을 넘겨도 제자리다 (실측으로 확인).
3개 상한이 변동 폭도 묶는다. 아래 카드는 조금 움직이는데, 「상단 고정 · 아래로 늘어나는 것은
허용」 이라는 기존 규칙 안이다.

**빈 상태**를 두 가지로 나눈다. 메모가 아예 없으면 쓰는 법을 안내하고(`위 연필로 …`),
그 달만 비었으면 `9월 메모 없음` 으로 사실만 말한다. 전자는 온보딩, 후자는 정보다.

### 「전체 메모」는 모달이 아니라 화면이다

처음엔 모달이었는데 두 가지가 걸렸다.

- 스크롤·검색으로 **오래 머무는 곳**인데 모달은 잠깐 결정하는 그릇이다
- 여기에 보기 모드까지 얹으면 겹침이 **4단**이 된다 (전체메모 → 보기 → 편집 → 날짜선택기).
  백드롭이 넷 겹쳐 화면이 새까매진다

그래서 본문(`#mainView`)을 숨기고 `#notesPage` 를 띄우는 **화면 전환**으로 바꿨다.
별도 HTML 파일이 아니다 — 그러면 열 때마다 앱이 처음부터 다시 부팅되고 동기화도 다시 돈다.

겹침은 두 겹으로 줄었다.

| 요소 | back / box |
|---|---|
| 메모 팝업 | 58 / 59 |
| 날짜 선택기 | 60 / 61 |
| 공유 카드 | 62 / 63 |

화면이 되면서 **목록 높이를 고정하던 해킹이 사라졌다.** 모달일 땐 가운데 정렬이라 검색어를 한
글자 칠 때마다 결과 수에 따라 높이가 바뀌고 위아래로 두 배 튀었다(날짜 선택기와 같은 함정).
화면은 위에서 아래로 흐르므로 그냥 자연스럽게 늘어난다.

**헤더 · 분류 · 검색이 통째로 sticky** 다(`.page-top`). 목록을 아무리 내려도 거르고 찾는 수단이
늘 손에 있다. 실측 **142px** — 667px 화면에서도 21%라 목록에 525px 가 남는다.

기간 패널만 그 위에 떠서(`position: absolute`) 열어도 고정 영역이 커지지 않는다.

**고정 바는 좌우로도 흘려 화면 폭을 꽉 채워야 한다**(`margin: … -16px; padding: … 16px`).
`.wrap` 폭(398px)에만 맞췄더니 양쪽 16px 거터가 비어, 화면 끝까지 뻗는 월 머리글이
그 틈으로 비쳐 **고정 바 뒤가 겹쳐 보였다.** 스크롤 컨테이너를 나눠도 고쳐지지만 그럴 문제가
아니다 — 원인은 스크롤을 공유하는 것이 아니라 바가 내용보다 32px 좁았던 것뿐이고,
컨테이너를 나누면 `window.scrollY` 기반 점프 로직과 모바일 관성 스크롤·주소창 접힘까지
다시 다뤄야 한다.

검색창 안내는 `메모 검색` 하나다. 날짜로도 걸리지만(`filteredNotes` 가 날짜 문자열을 본다)
굳이 알리지 않는다 — 이제 연·월 그룹과 연도 점프가 있어 날짜로 찾을 일이 없다.

### 목록은 연·월로 묶는다

항목이 `08-07` 만 보여 주던 때는 2024년 8월 7일과 2026년 8월 7일이 화면상 완전히 같았다.
이제 `YYYY-MM` 으로 묶고 머리글에 **연도를 늘 함께** 쓴다 (`2026년 8월  3개`).

머리글은 실선 한 줄이 아니라 **화면을 가로지르는 띠**다 (`margin: 0 -16px` 로 `.wrap` 좌우 패딩을
흘려 낸다). 하이라인으로는 스크롤 중에 눈에 안 들어와 구분 역할을 못 했다.
해가 바뀌는 곳은 **간격과 중립색 선(`--mount`)으로만** 끊는다.
처음엔 accent 선에 accent 글자를 썼는데, 「여기서 해가 바뀐다」가 아니라
「그 달이 특별하다」로 읽혔다. 글자 색은 다른 달과 똑같이 둔다.

항목 날짜는 `07(금)` — 연·월은 머리글이 맡으므로 중복을 없앴고, 요일은 남겼다.
「그 금요일 수업」 하고 기억을 맞춰 보는 데 쓸모가 있다.

### 「더 보기」를 없앤 이유 — 문제는 렌더가 아니라 길이였다

5개씩 늘리는 방식이라 2년 전 메모에 닿으려면 수십 번 눌러야 했다. 실측해 보니:

| 기간 | 메모 | 전체 렌더 | DOM 노드 | 페이지 높이 |
|---|---|---|---|---|
| 1년 | 156 | 0.8 ms | 819 | 10,748 px |
| 3년 | 468 | 2.0 ms | 2,451 | 31,672 px |
| 5년 | 780 | 3.4 ms | 4,083 | 52,596 px |
| 10년 | 1,560 | 7.2 ms | 8,163 | 104,906 px |

**10년치를 통째로 그려도 7.2 ms 다.** 나눠 그릴 이유가 없었다.
진짜 문제는 페이지가 **10만 px(약 107화면)** 로 길어져 스크롤로는 도달할 수 없다는 것이고,
그건 페이징이 아니라 **점프**로 풀어야 한다.

달력 카드 스트립의 `3개 + N개 더` 는 그대로 뒀다 — 거긴 카드 안이라 길어지면 안 되고,
한 달치라 애초에 짧다.

### 「날짜로 이동」 버튼 하나 — 연도를 늘어놓지 않는 이유

연도를 칩으로 상시 노출하면 **연차가 쌓일수록 고정 영역이 커진다.** 실측:

| 연도 | 연도 줄 | 고정 영역 (667px 화면) |
|---|---|---|
| 3~5개 | 1줄 | 185 px (27%) |
| 8개 | 2줄 | 222 px (33%) |
| 12개 | 3줄 | 259 px (38%) |
| 20개 | 4줄 | 295 px (**44%**) — 분류 칩이 2줄이면 약 50% |

20년차 수련자에게 화면 절반이 머리말이 되는 셈이다. 그래서 연도와 월을 **한 패널에 넣고
헤더의 달력 아이콘(`날짜로 이동`)으로 접었다.** 고정 영역은 연도 수와 무관하게 **142px 고정**이다.

버튼은 옆의 `✎` 와 **같은 `.icon-btn`** 이다. 처음엔 `기간 ▾` 텍스트였는데 이름이 무엇을 하는지
모호했고(실제 동작은 연·월을 골라 그 지점으로 뛰는 것), `▾` 표식도 너무 작아 눌리는 것으로
안 읽혔다. 열려 있는 동안은 아이콘을 accent 로 칠해 이 버튼이 연 것임을 보인다.

**패널은 `.page-head` 안에 둔다.** `.page-top` 의 자식으로 두면 `top: 100%` 가 분류·검색까지
지난 지점이 되어 버튼에서 100px 넘게 떨어져 열린다 — 무엇이 열린 건지 알 수 없다.
지금은 버튼 아래 6px 다.

패널을 열면 **최신 해가 이미 펼쳐진 채**로 뜬다 — 흔한 경우(올해 안에서 이동)가 두 번 탭이면
끝나고, 옛날로 갈 때만 세 번이다. 연도 칩은 **고르기만** 하고 이동은 월을 누를 때 한 번만
한다. 연도에서 바로 움직이면 그 위를 패널이 덮고 있어 뭐가 움직였는지 보이지 않는다.

목록은 `filteredNotes()` 에서 뽑으므로 분류·검색을 걸면 남은 기간만 칩으로 남는다.
달이 하나뿐이면 건너뛸 데가 없으므로 버튼 자체를 숨긴다.

**월 패널은 목록 위에 떠 있다**(`position: absolute`). 자리를 차지하게 두면 펼칠 때마다
고정 영역이 커져 분류 칩과 검색창이 화면 밖으로 밀려난다. 떠 있으면 고정 영역 높이가
그대로라 `--notes-stick` 도 흔들리지 않는다.

**`behavior: "smooth"` 를 쓰지 않는다.** 몇 년을 건너뛰면 수만 px 라 한참 흐르고,
그동안 화면이 흐려 어디로 가는지 알 수 없다. 점프는 순간이동이어야 한다.
대신 순간이동은 「눌렸다」는 신호가 없으므로 **도착한 머리글을 1.1초 밝힌다**(`flashHead`).
어디에 닿았는지까지 함께 알려주는 셈이다.

### 함정 셋 — 전부 「눌러도 반응이 없다」로 나타났다

**1. sticky 요소의 좌표는 실제 위치가 아니다.** `jumpTo` 가 머리글을 재면 이미 붙어 있는
위치(=`--notes-stick`)를 돌려주므로 `목표 = scrollY + stick − stick = scrollY` 가 되어
**이미 지나온 달로 되돌아갈 수 없었다.** `offsetTop` 도 같은 값을 준다.
그래서 감싸는 `.note-group`(static)을 재도록 바꿨다. 덤으로 머리글이 그룹 안에서만 붙어,
지나간 머리글이 다음 것에 밀려나는 제대로 된 동작이 됐다.

**2. `[hidden]` 은 클래스 한 줄에 진다.** `.jump-months { display: grid }` 가 브라우저 기본
`[hidden] { display: none }` 을 이겨, 숨긴 패널이 화면에 떠 **아래 분류 칩의 클릭을 먹었다.**
지금은 `[hidden] { display: none !important }` 를 전역에 둔다.

**3. 바깥 클릭 감지는 캡처 단계에서.** 버블 단계에서는 칩의 `onclick` 이 먼저 돌며
`renderJump` 가 칩을 다시 그려, `e.target` 이 이미 DOM 에서 떨어져 나간 뒤다 —
`contains()` 가 false 라 방금 연 패널을 즉시 닫아 버린다.

마지막 그룹도 맨 위까지 올라올 수 있어야 하므로, 모자란 만큼만 목록에 아래 여백을 준다
(`syncStickyOffset` 이 같은 프레임에서 계산). 넉넉히 주면 바닥에 빈 공간이 남는다.

**칩 줄을 가로 스크롤로 두면 안 된다.** 처음엔 `overflow-x: auto` + 스크롤바 숨김으로 만들었는데,
12개월은 폭을 넘고(430px 화면에서 568px) **데스크톱 마우스로는 가로 스크롤을 할 수 없어**
뒤쪽 넉 달이 아예 닿지 않았다. 지금은 연도는 `flex-wrap`, 월은 **6칸 그리드**(12개월이 정확히
두 줄)로 두어 넘치면 줄을 바꾼다.

> 이 버그가 테스트를 그냥 통과했다. Playwright 의 `click()` 은 요소를 화면 안으로 **스크롤해
> 넣은 뒤** 누르기 때문이다. 그래서 지금은 칩마다 좌표를 잡아 `elementFromPoint` 가 그 칩을
> 돌려주는지 확인한다 — 화면 밖에 있으면 바로 걸린다. 320 / 430 / 768 px 에서 검사한다.

### sticky 두 겹 — 오프셋을 JS 가 맞춘다

`.page-top`(헤더+점프바)이 `top: 0`, 월 머리글이 그 **아래**에 붙어야 한다.
점프바는 연도를 펴면 높이가 변하므로 CSS 상수로 못 박을 수 없다.
`syncStickyOffset()` 이 재서 `--notes-stick` 에 넣고, 머리글은 `top: var(--notes-stick)`.

**그 측정을 `requestAnimationFrame` 으로 미룬다.** 목록이 3만 px 가 넘는데 렌더 직후
`getBoundingClientRect()` 를 부르면 동기 레이아웃이 강제돼 렌더가 **2 ms → 17 ms** 로 뛴다.
검색은 한 글자마다 다시 그리므로 그 값을 매번 문다.

### 뒤로가기 — 오버레이 스택 (`app.js`)

한때는 **「전체 메모」만** 히스토리를 쌓았다. 그래서 본문에서 연 메모 팝업이나 공유 카드는
폰 뒤로가기로 닫히지 않고 **앱을 나가 버렸다.** 한 화면에서는 되고 다른 화면에서는 안 되는
것이 가장 나쁘다 — 사용자는 「뒤로가기 = 닫기」를 이미 배운 뒤였다.

지금은 뜨는 것마다 스택에 얹고 히스토리를 한 칸 쌓는다 (`openOverlay`).

| 오버레이 | 포커스 가둠 |
|---|---|
| 메모 팝업 | ✔ |
| 날짜 선택기 | ✔ |
| 공유 카드 | ✔ |
| 전체 메모 | ✘ — 모달이 아니라 화면이다 |

닫는 길이 둘인데 **둘 다 같은 곳으로 모인다.**

- 버튼·Escape → `dismissOverlay(name)` 가 즉시 닫고 그만큼 `history.go(-n)`
- 하드웨어 뒤로가기 → `popstate` 가 `history.state.mt`(깊이)를 보고 그 깊이까지 닫는다

**깊이를 state 에 적어 두는 것이 핵심이다.** 「한 칸 되감았다」가 아니라 「몇 번째 칸에
도착했다」를 알아야, 여러 칸을 한 번에 되감아도(`history.go(-2)`) 정확히 그만큼만 닫힌다.

- **URL 인자를 주지 않는다.** `file://` 에서 주소를 바꾸면 브라우저에 따라 막힌다
  (스모크 테스트가 `--file` 로 그 경로를 함께 확인한다. 인자 없는 `pushState` 는 동작한다)
- `pushState` 가 막히면 그 오버레이만 히스토리 없이 뜬다 — 기능이 죽지는 않는다
- **`history.scrollRestoration = "manual"`** 이 필수다. 기본값(`auto`)이면 `history.back()` 이
  브라우저의 자동 스크롤 복원을 발동시켜, 우리가 옮겨 둔 본문 스크롤 위치를 0 으로 덮어쓴다.
  이것 때문에 「돌아오면 보던 자리」가 동작하지 않았다
- 본문을 되살린 직후엔 문서 높이가 아직 갱신 전이라 `scrollTo` 가 0 으로 잘린다.
  `scrollHeight` 를 읽어 리플로우를 강제한 뒤 옮긴다
- 닫을 때 **열기 전 포커스로 되돌린다.** 안 그러면 포커스가 `body` 로 떨어져 탭 순서를 잃는다

### 보기 모드와 편집 모드

목록 항목을 누르면 **보기** 로 열린다. 읽으려고 눌렀을 뿐인데 곧바로 폼이 잡히면
실수로 고칠 위험이 있고, **모바일에선 열 때마다 키보드가 올라온다.**
`focus()` 는 편집 모드에서만 부른다.

| 들어오는 곳 | 모드 |
|---|---|
| 목록 항목 (달력 카드 · 전체 메모) | `view` |
| 연필 아이콘 (달력 헤더 · 전체 메모 헤더) | `edit` — 새 메모라 볼 게 없다 |
| 보기 모드의 `편집` | `edit` |

바닥 버튼은 `편집`(보기) ↔ `저장`(편집) 으로 갈리고 둘 다 accent 다 —
서로를 대신하는 자리라 같은 강조를 준다. `삭제` · `닫기` 는 공통.

**본문에는 `overflow-wrap: anywhere` 가 필요하다.** 앱 전역이 `word-break: keep-all`
(한글이 단어 중간에서 안 꺾이게)인데, 공백 없이 길게 쓴 한글은 그 규칙 때문에 아예 안 꺾여
한 줄로 삐져나가고 뒷부분이 보이지 않는다. 목록의 `.note-body` 도 같다.

### 분류 — 초기값 5종, 사용자가 더하고 지운다

수업 · 세미나 · 대회 · 영상 · 기타로 시작하되 **상수가 아니라 데이터다** (`noteDoc.tags`).
자유 입력 태그가 아니라 관리되는 목록인 이유는 칩 UI 로 한 번에 고를 수 있고,
필터가 예측 가능하며, 오타로 같은 분류가 갈라지지 않기 때문이다.

**1개 이상 10개 이하**, 이름은 10자 이하. 0개면 메모를 쓸 수 없고, 10개를 넘으면 칩이
화면을 삼킨다.

편집은 메모 팝업의 `분류` 줄 오른쪽 **편집** 버튼으로 들어간다. 편집 모드에서 칩은
선택지가 아니라 삭제 버튼이 되고(점선 테두리 + 빨간 `×`로 모드가 구분된다) 끝에 `＋ 분류` 가 붙는다.
설정 카드가 아니라 팝업에 둔 이유는 **분류가 아쉬운 순간이 메모를 쓰는 순간**이기 때문이다.
"설정에 가서 추가하세요" 는 그 흐름을 끊는다.

기본 분류는 id 가 영문이고 **사용자가 만든 분류는 이름 자체가 id 다.** 이름 변경 기능이
없으므로 둘을 나눌 이유가 없고, 지웠다 같은 이름으로 다시 만들면 옛 메모와 다시 이어진다.

**쓰던 분류를 지울 때가 까다롭다.** 그 분류를 가리키던 메모가 어느 필터에도 안 걸리는
유령이 되기 때문이다. 그래서 삭제 확인창에서 몇 개가 어디로 옮겨지는지 밝히고
(`메모 3개는 「수업」으로 옮겨집니다`) 첫 분류로 재배정한다.
**옮긴 메모의 `at` 도 갱신해야** 그 변경이 다른 기기로 전파된다.

분류 이름이 사용자 입력이라 **조사를 하드코딩할 수 없다.** `toParticle()` 로 받침을 보고
`로`/`으로` 를 고른다 (수업 → 수업**으로**, 기타 → 기타**로**, 서울 → 서울**로**).

분류도 출석과 같은 툼스톤(`removedTags`)을 쓴다. 합집합만 쓰면 한쪽에서 지운 분류가
다른 기기에서 되살아난다 — 이 프로젝트가 출석·승급 이력에서 두 번 밟은 함정이다.

### 500자 상한

"간단히 기록" 용도이고, 상한이 있어야 크기를 예측할 수 있다.
저장 시 `slice(0, 500)`, 복원 검증에서는 초과하면 **파일 전체를 거부**한다 —
복원 경로에서 조용히 잘라내는 건 데이터 손실이기 때문이다.

### 검색은 150 ms 디바운스

메모 검색은 이 앱에서 **유일하게 선형 비용이 체감될 수 있는 경로**다. 입력 한 글자마다
전체 본문을 훑는데, 상한을 채운 메모 1,500건이면 한 번에 12.9 ms 로 한 프레임(16.7 ms)에
육박한다. 타이핑이 멈춘 뒤 한 번만 돌게 한다.

분류 필터와 「더 보기」에는 디바운스가 없다 — 한 번의 탭이라 지연이 곧 반응 없음으로 읽힌다.

### 공유 카드에는 넣지 않는다

카드는 남에게 보내는 것이고 메모는 혼자 보는 것이다.

## 공유 카드

「기록」 카드 헤더의 공유 아이콘, 그리고 승급을 기록한 직후에 열린다.
승급 직후를 잡는 이유는 자랑 동기가 그때 가장 높기 때문이다 — 토스트만 띄우고 끝내던 자리를 대체한다.

### 왜 캔버스에 직접 그리는가

DOM 을 이미지로 만들려면 html2canvas 같은 라이브러리가 필요한데, 이 프로젝트는 의존성이 0이다.
그래서 `share-card.js` 에서 **캔버스에 처음부터 그린다**.
벨트는 `paintBelt()` 의 구조(둥근 사각형 + 오른쪽 42% 검은 팁 + 흰 그랄)를 좌표계만 바꿔 옮겼다.
색은 `styles.css :root` 와 같은 값을 JS 상수로 복제한다 (`C` 객체).

카드는 1080×480 을 2배 스케일로 그린다. `devicePixelRatio` 를 쓰지 않는 이유는
기기마다 다른 결과가 나오면 공유물의 품질이 들쭉날쭉해지기 때문이다.

### 카드에는 띠와 연차만 — 앱을 늦게 시작한 사람 문제

주짓수는 6년 했는데 앱은 지난달부터 썼다면 총 출석·연속 주·잔디가 실제 수련량과 무관해진다.
6년차가 초보처럼 보이는 카드는 아무도 공유하지 않는다.
`…부터 기록` 을 덧붙여 오해를 줄이는 방법도 써 봤지만, 근본적으로 **공유하고 싶지 않은 그림**이었다.

그래서 부정확할 수 있는 것을 전부 덜어내고, **앱 사용 시작 시점과 무관하게 정확한 둘만** 남겼다.

| 카드에 담는 것 | 왜 정확한가 |
|---|---|
| 벨트·그랄 그래픽 | 사용자가 직접 입력한 승급 이력에서 파생 |
| `N년 M개월째 땀 흘리는 중` | `startedAt` 하나로 결정 |

문구는 `share-card.js` 위쪽 상수로 뺐다 — `TAGLINE` 과 `spanLine()`.
`spanLine()` 은 경계를 따로 처리한다: 시작일이 오늘이면 `오늘 첫 수련`, 미래면 `곧 시작` —
그러지 않으면 `0일째 땀 흘리는 중` 같은 문장이 나온다.
`TAGLINE`(`꾸준함이 벨트를 만든다`)은 승급 모드엔 넣지 않는다. 이미 축하 문구가 있어 겹친다.

벨트 **이름 텍스트도 쓰지 않는다**. 주짓수 하는 사람은 띠만 보면 알고, 모르는 사람에겐
이름이 있어도 의미가 없다. 카드는 성적표가 아니라 명함에 가깝다.

단, 메신저에 이미지와 함께 붙는 **공유 텍스트**(`shareText()`)에는 벨트 이름을 남긴다 —
받는 사람에게 맥락을 주는 건 그 줄의 몫이다.

앱 화면(「기록」 카드의 잔디·3수치·`…부터 기록` 표기)은 그대로 둔다.
내 데이터를 내가 보는 화면에서는 맥락을 알고 보기 때문에 문제가 되지 않는다.

**레이아웃 주의** — `drawBelt()` 는 벨트 밖으로 받침(`beltH * 0.18`)을 더 그린다.
세로 중앙 정렬을 계산할 때 이 두께를 빼먹으면 글자가 띠에 달라붙는다.

### 공유는 3단 폴백

환경마다 되는 게 달라 순서대로 내려간다.

1. `navigator.canShare({files})` → `navigator.share()` — 모바일. **https 필수**라 Pages 에서만
2. `navigator.clipboard.write(ClipboardItem)` — 데스크톱 브라우저 다수
3. `<a download>` 로 PNG 저장 — 마지막 보루

`링크 복사` 는 항상 따로 제공한다. 이미지가 안 되는 텍스트 전용 채널을 위해서다.

**Blob 은 모달을 열 때 미리 만든다.** iOS Safari 의 `navigator.share` 는 사용자 제스처
안에서만 동작하는데, 공유 버튼을 누른 뒤 `await drawShareCard()` 를 하면 그 사이에
제스처 맥락이 끊긴다. `sharing` 플래그로 연타도 막는다 — 공유 시트가 두 번 뜨면 곤란하다.

빌드 도구·번들러·의존성이 없다. 파일을 그대로 올리면 그대로 동작한다.

### 로드 순서 — 걸리는 건 `main.js` 하나뿐

전부 일반 스크립트(`<script src>`)라 **전역 스코프를 공유한다.** 파일 사이의 참조는 거의 전부
함수 본문 안에서 일어나므로, 호출 시점엔 모든 파일이 로드돼 있어 순서와 무관하다.

순서가 실제로 중요한 것은 **최상위에서 다른 파일의 값을 읽는 경우**뿐이다.

- `main.js` — 최상위에서 `$` 로 DOM 을 잡고 부팅한다. **반드시 마지막**
- 나머지 파일의 최상위는 자기 안에서 닫혀 있다 (`let state` · `let noteDoc` · `let sync`)
- 바인딩을 각 파일 하단에 흩지 않고 `main.js` 로 모은 것도 이 제약을 한 곳에 가두기 위해서다

주의할 함정 하나 — **같은 이름의 최상위 `const` 가 두 파일에 있으면 로드 즉시 런타임 에러**다.
`const` 는 `window` 의 속성이 되지 않고 전역 렉시컬 스코프에 들어가는데, 그 스코프는 파일이
공유하기 때문이다. 같은 이유로 테스트가 `pg.evaluate` 에서 찌르는 전역
(`state` · `noteDoc` · `render()` · `mergeNotes()` …)은 분리 후에도 그대로 살아 있다.

### 경계를 이렇게 그은 이유

- **백업은 나누지 않았다.** 파일 하나에 두 문서를 담으므로 `backupDoc`·`validateBackup`·
  `importData` 는 본질적으로 코어와 메모를 함께 본다. `app.js` 에 두고 `notes.js` 의
  상수를 호출 시점에 참조한다
- **병합 함수는 각자의 문서 파일에.** `mergeStates`/`sameState` 는 `app.js`,
  `mergeNotes`/`sameNotes` 는 `notes.js`. 둘이 공유하는 `pickByStamp`·`newerEpoch` 만
  `app.js` 에 두고, `sync.js` 는 읽고·엮고·바뀐 파일만 올린다
- **`stampMap` 은 `app.js`** — 코어 `normalize` 와 `normalizeNotes` 가 함께 쓴다

### ES 모듈·프레임워크·빌드를 넣지 않는 이유

한때 이 문서에는 *"일반 스크립트로 나누면 파일만 갈릴 뿐 결합은 그대로라, 진짜로 나누려면
ES 모듈이 필요하다"* 고 적혀 있었다. **이건 과장이었다.**

실제로 아픈 것은 결합이 아니라 **탐색**이었다. 2,125줄짜리 파일에서 메모 코드를 찾는 일이
번거로웠던 것이지, 메모 코드가 `state` 를 건드려서 사고가 난 적은 없다.
그리고 탐색은 일반 스크립트 분리만으로 완전히 해결된다 — 실제로 그렇게 나눴고,
`app.js` 는 1,350줄로 돌아왔다.

ES 모듈이 더 주는 것은 **강제된 캡슐화**뿐인데, 그 대가가 크다.

- **테스트가 전역에 의존한다.** `test/harness.mjs` 가 `node:vm` 컨텍스트에 `app.js` ·
  `notes.js` 를 그대로 올리고 최상위 이름(`normalize` · `mergeStates` · `validateBackup` …)을
  꺼내 쓴다. 앱 코드에 테스트 전용 export 를 한 줄도 넣지 않아도 되는 것이 이 구조의 값이다.
  모듈이 되면 하네스를 버리고 앱에 export 를 심거나 UI 조작만으로 재작성해야 한다
- **`file://` 로 못 연다.** 스모크 테스트가 `--file` 로 그 경로를 함께 확인하고,
  개발 중 파일을 더블클릭해 보는 흐름도 사라진다

혼자 쓰는 무빌드 앱에서 회수되지 않는 거래다.

**프레임워크**는 더 명확하다. `render()` 가 전부 다시 그리는데 실측 3 ms(10년치)·8 ms(30년치)라
성능 문제가 없고, 반복 요소는 이미 `paintBelt()` · `beltEl()` 로 재사용 중이다.
얻는 것 대비 전면 재작성 + 빌드 + 배포 2단계의 비용이 회수되지 않는다.

가장 긴 함수가 91줄이고, 이 프로젝트에서 잡은 버그들은 분산 동기화 설계
(툼스톤·`epoch`·merge O(n²))와 CSS(레이아웃 시프트·달력·모달 높이) 문제였다.
**구조 때문에 생긴 버그는 아직 하나도 없다.**

다시 검토할 조건 — 줄 수가 아니라 증상으로 적는다. 「2,000줄을 넘으면」 이라고 세어 두었더니
넘긴 시점에 진짜 문제가 있는지와 무관하게 알람이 울렸다.

- **섹션 배너로 찾기 어려워질 때** (한 파일이 대략 1,500줄을 넘고 관심사가 섞이기 시작할 때)
- 타입 실수가 잦아 TypeScript 가 필요해질 때
- 여러 사람이 동시에 손대기 시작할 때

### 화면 순서

**헤더(벨트) → 출석 달력(+메모) → 기록 → 승급 진행도 → 로드맵 → 설정**

승급 진행도와 로드맵은 추적을 꺼 두면 통째로 빠진다. 기본 화면은
**헤더 → 달력(+메모) → 기록 → 설정** 이다 — 어느 체육관에서나 맞는 것만 남는다.

「기록」 카드(잔디·수치)가 이 앱에서 가장 동적인 부분이라 달력 바로 아래에 둔다.
승급 진행도는 7개월/90일 구간에서 하루 0.5%씩만 움직여 자주 볼 이유가 적어 그 아래로 내렸다.

메모는 **카드가 아니라 달력 카드의 일부다.** 처음엔 「기록」 아래 접힌 카드로 뒀는데,
쓰기 입구(달력 헤더 연필)와 읽는 곳이 카드 하나를 사이에 두고 떨어져 있었다.
방금 쓴 걸 확인하려면 스크롤해서 카드를 펼쳐야 했다.

출석 체크 전용 버튼은 두지 않는다. 달력의 오늘 칸과 하는 일이 똑같아 중복이기 때문이다.
대신 오늘 칸에 강조 테두리를 두고, 달력 위에 `오늘 8/6(목) · 아직 체크 전` 같은 상태 줄을 둔다.

### 취소에는 되돌리기를 붙인다

같은 탭인데 두 방향의 성격이 다르다.

| | 체크 | 취소 |
|---|---|---|
| 빈도 | 매일 | 어쩌다 한 번 |
| 잘못했을 때 | **바로 보인다** (없던 초록이 생긴다) | **티가 안 난다** (초록이 회색으로 바뀔 뿐) |
| 회복 | 다시 누르면 끝 | 어느 날이었는지 기억해야 한다 |

**막는 대신 되돌린다.** 취소하면 토스트에 `되돌리기` 가 함께 뜨고, 그동안(6초) 누르면
원래대로 돌아온다. 확인창(`confirm`)도 후보였지만 쓰지 않았다.

- 출석 토글의 피드백은 **원래 토스트**다. 거기에 확인창을 얹으면 같은 동작이 두 가지
  방식으로 말을 건다
- 매일 하는 동작 앞에 시스템 대화상자를 세우면 제일 자주 하는 일이 느려진다.
  체크는 안 묻고 취소만 묻는다 해도, 잘못 눌러 취소하는 흐름 자체가 2탭이 된다

**토스트가 유일한 회복 수단이면 안 된다.** 6초는 놓칠 수 있고, 스크린리더는 사라지는 버튼에
닿기 어렵다. 출석은 그 칸을 다시 누르면 언제든 돌아오므로 이 버튼은 지름길일 뿐이다.

되돌릴 때 **켠 시각은 원래 값이 아니라 지금**이다 (`checkDay`). 취소가 이미 Gist 에
올라갔다면(디바운스 1.5초) 원격 툼스톤이 원래 시각보다 늦어, 되살린 출석이 다음 병합에서
도로 사라진다. 되돌리기는 「그때로 복원」이 아니라 「지금 다시 체크」다.

라이브 영역(`aria-live`)은 **메시지에만** 건다. 버튼까지 묶으면 토스트가 뜰 때마다
버튼 이름이 함께 읽힌다.

### 저장이 실패하면 성공 안내를 띄우지 않는다

`localStorage` 가 꽉 차면 `writeLocal()` 이 「저장 실패」를 알린다. 그런데 부르는 쪽이
이어서 「출석 완료」를 띄우면 **그 경고가 즉시 덮인다** — 저장되지도 않은 것을 성공으로 알리는 셈이다.

그래서 `save()` · `saveNotes()` 가 **성공 여부를 돌려주고**, 부르는 쪽은 성공했을 때만
완료 안내를 띄운다. 예전에는 「토스트를 먼저, 저장을 나중에」 하는 순서에 기대고 있었는데,
그건 코드를 조금만 옮겨도 깨지는 규칙이었다 (실제로 한 번 깨뜨렸고 테스트가 잡았다).

### 승급 진행도 — 두 예측을 나란히

기준을 못 채운 동안에는 두 날짜를 함께 보여준다.

```
기간 D-72 · 출석 27일 부족
승급식 — 빠르면 10/30(금) · 이 페이스면 4/30(금)
```

- **빠르면** — 하루도 빠지지 않았을 때의 이론상 최단. 출석은 하루 한 번뿐이라
  남은 N일을 채우려면 최소 N일이 걸리는 점까지 반영한다
- **이 페이스면** — 최근 4주 실제 페이스로 계산한 현실적인 날짜

둘이 벌어진 폭이 곧 경고다. 같으면 `지금 페이스로도 동일`, 최근 출석이 없으면
`최근 출석이 없어 페이스 예측 불가` 로 바뀐다.

### 기록 카드 — 세 지표와 잔디

승급까지 7개월/90일이 걸리는 구간에서는 진행률 바가 하루에 0.5%씩만 움직여 화면이 정체된다.
그래서 성격이 겹치지 않는 세 숫자와 누적 그림을 둔다.

```
172회        58주        3.0회
총 출석    ● 연속     최근 4주 주당
 (누적)     (유지)       (속도)
```

- 단위(`회`·`주`)를 숫자에 붙여 라벨을 안 읽어도 구분된다
- **연속만 끊길 수 있는 값**이라 점으로 이번 주 상태를 표시한다.
  아래 문장이 `이번 주 출석 완료` / `이번 주 아직` 으로 함께 바뀐다
- `이번 달 N회 · 지난달 같은 기간 대비 +N` — 이번 달은 진행 중이므로
  지난달 **같은 날짜까지**와 비교해야 공평하다
- **잔디** — 최근 1년(53주) 출석 격자. 진행률과 달리 **되돌아가지 않는 누적 기록**이라
  오래 쓸수록 채워진다. 승급일은 주황으로 찍히고, 캡션의 횟수는 **표시 구간 안의** 출석 수다

**잔디 칸을 누르면 달력이 그 달로 간다.** 「이 근처에서 한참 쉬었네」를 발견하는 곳이 잔디인데,
거기까지 가려면 달을 하나씩 넘겨야 했다. 칸이 371개라 각각에 붙이지 않고 격자에 위임하고,
날짜는 `data-d` 로 싣는다. 미래 칸에는 싣지 않는다(갈 수 없는 달이다).

달력은 잔디보다 **위에** 있으므로 옮기기만 하면 화면 밖에서 벌어진다. `scrollIntoView` 로
카드까지 데려가고, 순간이동이라 신호가 없으니 **도착한 카드를 1.1초 밝힌다**
(메모 점프의 `flashHead` 와 같은 방식).

격자는 계속 `aria-hidden` 이고 칸은 탭 순서에 넣지 않는다 — 같은 이동을 달력의 `‹ ›` 가
이미 제공하는 **지름길**이라, 371칸을 탭으로 지나가게 만드는 쪽이 손해다.

**연속(streak) 단위는 일이 아니라 주다.** 주짓수는 매일 하는 운동이 아니라
일 단위 연속을 쓰면 하루만 쉬어도 0이 되어 오히려 의욕을 꺾는다.
주(일~토)에 한 번이라도 나가면 이어진 것으로 보고, 이번 주는 아직 안 갔을 수 있으므로 끊긴 것으로 치지 않는다.

### 달력

항상 **6주(42칸)** 를 그린다. 달마다 5주·6주로 높이가 바뀌면 월을 연속으로 넘길 때
아래 내용이 밀려 오조작이 난다. 앞뒤 빈칸은 이웃 달 날짜로 채워 일반 달력처럼 보이게 하되,
**숫자만 흐리게 남기고 배경·테두리는 지운다** — 채움을 남기면 흐려진 녹색이
「승급 전 출석」과 구분되지 않는다. 이웃 달 칸은 누를 수 없다.

마지막 승급일 이전의 출석은 어둡게(`before-promo`) 그린다. 이건 **승급 날짜에만** 기대므로
추적을 꺼도 남는다 — 승급일 주황 점과 같은 성격이다. 그래서 범례에 「단계」라는 말을
쓰지 않는다(`승급 전 출석`). 추적이 꺼진 화면에는 「단계」라는 개념이 아예 없다.

칸 안의 표식은 둘이다. 승급일은 **우상단 노란 점**, 메모는 **하단 중앙 짧은 줄**.
자리를 나눠야 승급한 날에 메모까지 있어도 겹치지 않는다. 출석한 날은 배경이 초록이라
메모 줄만 어두운 색으로 뒤집는다.

헤더에는 월 이동(`‹ · 월 · ›`)과 메모 버튼이 함께 있다. 월 이동 셋을 `.cal-nav` 로 묶고
`flex:1 + space-between` 을 주는데, 묶기만 하고 폭을 안 주면 왼쪽에 뭉쳐 붙는다.
메모 버튼과의 간격도 넉넉히 벌린다 — 붙여 두면 「다음 달」의 짝처럼 읽힌다.

이웃 달·미래 칸은 `disabled` 다. CSS 의 `pointer-events: none` 은 클릭만 막고 **탭 순서에는
남아** 있어, 키보드로 훑으면 누를 수 없는 칸 스물몇 개를 지나야 했다.

누를 수 있는 칸에는 `aria-label`(`8월 15일 금요일 · 메모 있음`)과 `aria-pressed` 를 준다.
숫자만 두면 스크린리더에 「15」로 끝나 무슨 날인지도, 켜졌는지도 알 수 없다.

### 달력 칸을 길게 누르면 그날 메모

탭은 출석 토글이라 메모에 남는 동작이 롱프레스뿐이었다. 신경 쓸 것이 셋인데,
**전부 「눌렀는데 엉뚱한 일이 난다」로 나타난다.**

1. **롱프레스 뒤에 오는 `click` 을 반드시 먹어야 한다.** 안 그러면 메모를 열면서 출석까지
   토글된다 — 이 기능에서 가장 치명적인 오작동이다. `lpFired` 플래그를 세우고 `onclick` 이
   `consumeLongPress()` 로 한 번만 꺼내 쓴다 (다음 `pointerdown` 이 초기화)
2. **스크롤 시작과 구분해야 한다.** 10px 넘게 움직이면 취소하고, `pointermove` 가 오지 않는
   관성 스크롤을 대비해 `scroll` 에서도 취소한다
3. **컨텍스트 메뉴 셋을 각각 막아야 한다.** 안드로이드 롱프레스와 데스크톱 우클릭은
   `contextmenu` 에서(막는 김에 우클릭도 메모로 돌린다), iOS 의 선택 콜아웃은
   CSS `-webkit-touch-callout: none` + `user-select: none` 으로

안드로이드는 타이머와 `contextmenu` 가 **둘 다** 뜨므로 `lpFired` 로 한 번만 열리게 한다.

칸은 매 렌더마다 새로 만들어지므로 핸들러는 **격자에 위임**한다. 발견되기 어려운 동작이라
메모가 하나도 없을 때의 안내 문구에 두 입구를 함께 적는다.

키보드에는 롱프레스가 없다 — 그쪽은 연필 → 날짜 선택기가 같은 일을 한다.

### 날짜 선택기

`<input type="date">` 의 네이티브 달력은 **시작 요일을 브라우저·OS 로케일이 정하고
CSS·HTML 로 바꿀 수 없다.** 출석 달력과 같은 일요일 시작으로 맞추려고 직접 만들었다
(`openPicker` / `renderPicker`). 월·연 단위 이동, 오늘, 지우기를 제공하고
미래 날짜는 비활성이다.

출석 달력과 **같은 6주 고정 격자**를 쓴다. 팝오버가 가운데 정렬이라 높이가 변하면
위아래로 두 배 흔들려, 월을 연속으로 넘길 때 버튼 위치가 어긋난다.

주짓수 시작일·승급일·메모 날짜가 모두 이 하나를 쓴다. 메모 팝업 위에서 열리므로
z-index 를 그보다 높게 유지해야 한다 (메모 절의 표 참조).

### 설정 패널 순서

수련 데이터를 위에, 저장·백업을 아래에 둔다.

```
주짓수 시작일                                ← 유일한 직접 입력 텍스트값
승급 진행도 추적 (토글)                       ← 기본 꺼짐. 체육관 규정에 기대는 것들을 켠다
승급 이력                                    ← 현재 벨트·단계 시작일의 원천
기기 간 동기화 (GitHub Gist)                 ← 저장
백업 / 복원
전체 초기화
```

**토글을 승급 이력 바로 위에 둔다.** 둘은 별개지만 계속 헷갈리는 짝이라, 붙여 놓고
「꺼도 이력은 그대로 기록됩니다」를 그 자리에서 읽게 하는 편이 낫다. 떨어뜨려 두면
이력을 넣으러 온 사람이 토글을 못 보고, 토글을 끈 사람은 이력까지 꺼졌다고 오해한다.

스위치는 앱에서 유일한 불리언 컨트롤이라 그림만 새로 그리고 **알맹이는 진짜
`<input type="checkbox">`** 다 — 키보드 스페이스바와 스크린리더가 그냥 동작해야 한다.
초점 링은 화면 밖에 숨긴 input 대신 스위치에 옮겨 그린다.
