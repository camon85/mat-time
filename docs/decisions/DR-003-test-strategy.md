# DR-003. 테스트를 순수 함수(node:vm)와 브라우저(Playwright)로 나눈다

- **날짜**: 2026-08-07
- **상태**: 결정됨

## 맥락

저장소에 테스트가 하나도 없었다. 그런데 [`implementation.md`](../implementation.md) 는
ES 모듈을 쓰지 않는 근거로 *"테스트 9종을 전부 다시 써야 한다"* 를 들고 있었다 — 존재하지 않는
테스트가 설계 결정의 근거로 남아 있던 셈이다.

문제는 문서 불일치만이 아니다. 이 프로젝트에서 **틀리기 쉬운 것이 전부 순수 함수**다 —
`mergeStates` · `mergeNotes` · `pickByStamp` · `validateBackup` · `monthsElapsed` ·
`lastFridayOf`. 실제로 [DR-001](DR-001-per-item-sync-stamps.md) 의 병합 버그는 30줄짜리
스크립트로 즉시 재현됐다.

걸림돌은 앱 코드가 **일반 스크립트**라는 것이다. `import` 할 수 없고, 최상위 `const` 는
`globalThis` 의 속성이 되지도 않는다.

## 검토한 선택지

### 옵션 A: 전부 Playwright 로
브라우저를 띄우고 `page.evaluate` 안에서 전역을 찌른다 (예전 방식).

- 장점: 앱 코드에 손댈 필요 없음. UI 까지 같은 도구로
- 단점: 순수 함수 하나 고치는 데 **브라우저 부팅**이 붙는다. 실패했을 때 스택이 얕아
  원인을 찾기 어렵고, CI 없이 로컬에서 자주 돌리기엔 무겁다

### 옵션 B: ES 모듈로 바꾸고 그냥 import
- 장점: 표준적이고 도구가 다 붙는다
- 단점: `file://` 개발 흐름이 죽고, 전면 수정이다. 테스트를 위해 앱 구조를 바꾸는 셈

### 옵션 C: 앱에 테스트용 export 를 심는다
`if (typeof module !== "undefined") module.exports = {...}` 같은 것.

- 장점: 간단
- 단점: **앱 코드에 테스트 사정이 새어 들어간다.** 브라우저에서는 아무 의미 없는 줄이 남는다

### 옵션 D: node:vm 하네스 + 브라우저는 필요한 것만
`vm` 컨텍스트에 `app.js` · `notes.js` 를 **브라우저와 같은 방식으로**(전역 공유 스크립트 두 장)
올리고, 컨텍스트 안에서 이름을 모아 꺼낸다. 제스처·히스토리·포커스·오프라인만 Playwright.

- 장점: 앱 코드에 한 줄도 안 넣는다. 순수 함수 42종이 **1초 이내**에 돈다
- 단점: 하네스가 DOM 을 흉내내야 하고, vm 이 만든 객체는 realm 이 달라
  `deepStrictEqual` 이 그냥은 통과하지 않는다

## 고민 과정

D 의 단점은 하네스 파일 하나에 갇힌다 (`fakeDom()` 과 `plain()` 두 헬퍼). 반면 A 는 비용이
매번 들고, B·C 는 테스트 사정 때문에 앱을 바꾼다.

나누는 기준은 "레이어"가 아니라 **「브라우저가 정말 필요한가」** 로 잡았다. 롱프레스 후 click
억제, 뒤로가기 깊이, 포커스 복귀, 서비스 워커는 흉내낼 수 없으므로 진짜 브라우저로 눌러 본다.

## 결정

**옵션 D** 채택.

채택 이유: 앱 코드를 건드리지 않으면서 가장 위험한 로직을 가장 싸게 덮는다.
덤으로 "일반 스크립트라서 테스트가 전역에 의존한다"는 근거가 **실재하는 것**이 됐다.
