# DR-002. 오프라인 캐시는 stale-while-revalidate

- **날짜**: 2026-08-07
- **상태**: 결정됨

## 맥락

기록은 localStorage 에 있는데 **앱 껍데기를 받아오지 못해 화면 자체가 뜨지 않았다.**
지하 체육관·지하철·비행기에서 출석을 찍는 앱이라 이건 기능 하나가 아니라 전제의 문제다.

서비스 워커를 넣기로 한 것은 자명했고(대안이 없다), 캐시 전략에 선택지가 있었다.
이 프로젝트의 배포는 「파일을 푸시」 하나뿐이고 빌드·버전 태깅 단계가 없다는 점이 조건이다.

## 검토한 선택지

### 옵션 A: cache-first (버전 수동 갱신)
캐시에 있으면 그것만 쓰고, `CACHE_VERSION` 을 올릴 때만 새로 받는다.

- 장점: 가장 빠르고 예측 가능하다. 네트워크를 아예 안 탄다
- 단점: **버전 올리는 걸 잊으면 영영 옛 코드가 남는다.** 배포가 `git push` 뿐이라
  잊기 딱 좋고, 잊었을 때 증상이 「고쳤는데 안 고쳐졌다」라 진단도 어렵다

### 옵션 B: network-first
네트워크를 먼저 시도하고 실패하면 캐시.

- 장점: 항상 최신 코드
- 단점: **느린 회선에서 매번 기다린다.** 오프라인이 아니라 "신호가 약한 지하"가
  실제 환경인데, 그때 타임아웃까지 흰 화면을 본다

### 옵션 C: stale-while-revalidate
캐시를 즉시 주고, 뒤에서 받아 캐시를 갱신한다.

- 장점: 실행이 항상 빠르고, 잊을 것이 없다
- 단점: 코드 반영이 **한 번 늦다** (다음 실행부터)

## 고민 과정

A 의 단점은 "사람이 잊는다"이고 C 의 단점은 "한 번 늦다"인데, 하루 한 번 여는 앱에서
한 번 늦는 것은 사실상 즉시다. B 는 실제 환경(약한 신호)에서 가장 나쁘게 동작한다.

## 결정

**옵션 C (stale-while-revalidate)** 채택.

채택 이유: 잊어서 생기는 고장이 없고, 실제 사용 환경인 「신호가 약한 곳」에서 가장 빠르다.

## 영향

- `sw.js` — 같은 출처 GET 만 다룬다. **`api.github.com` 을 캐시하면 안 된다**
  (동기화가 옛 Gist 를 읽고 병합해 기록을 되돌린다). 200 이 아닌 응답도 넣지 않는다
- 캐시 이름(`mat-time-v1`)은 정리용이다. 코드 갱신을 위해 올릴 필요가 없다
- `file://` 에서는 등록을 건너뛴다 — 더블클릭 개발 흐름을 지킨다
- 스모크 테스트가 오프라인 진입을 확인한다 (`dev/smoke.py` — 「오프라인」 절)
- 재검토 조건: 배포에 빌드 단계가 생기면 A(버전 자동 주입)가 더 낫다
