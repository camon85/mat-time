# DR-004. 뜨는 것은 전부 히스토리 스택에 얹는다

- **날짜**: 2026-08-07
- **상태**: 결정됨

## 맥락

「전체 메모」 화면만 `history.pushState` 로 한 칸을 쌓고 있었다. 그래서 폰 뒤로가기가

| 상황 | 결과 |
|---|---|
| 전체 메모 안에서 연 메모 팝업 | 팝업만 닫힘 ✔ |
| 본문에서 연 메모 팝업 | **앱을 나감** ✘ |
| 공유 카드 (어디서든) | **앱을 나감** ✘ |

로 갈렸다. 한 화면에서 「뒤로가기 = 닫기」를 배운 사용자가 다른 화면에서 앱 밖으로
튕겨 나가는 것이라, 아예 안 되는 것보다 나쁘다.

## 검토한 선택지

### 옵션 A: 오버레이마다 따로 처리
공유 카드에도 `pushState` 를 붙이고, `popstate` 핸들러에 분기를 하나 더 넣는다.

- 장점: 변경이 작다
- 단점: 기존 방식이 「팝업을 닫고 히스토리를 **다시 쌓는**」 보정에 기대고 있어,
  분기가 늘수록 조합이 는다. 오버레이가 하나 더 생길 때마다 같은 함정을 다시 밟는다

### 옵션 B: 히스토리를 안 쓰고 뒤로가기를 가로챈다
`popstate` 마다 무조건 `pushState` 로 되밀어 앱을 못 나가게 한다.

- 장점: 스택 관리가 없다
- 단점: **아무것도 안 떠 있을 때도 앱을 나갈 수 없다.** 브라우저 뒤로가기를 망가뜨리는
  전형적인 안티패턴이다

### 옵션 C: 오버레이 스택 + 깊이를 state 에 기록
열 때 `pushState({mt: 깊이})`. 닫는 길은 둘이지만 한 곳으로 모은다 —
버튼·Escape 는 즉시 닫고 그만큼 `history.go(-n)`, 하드웨어 뒤로가기는 `popstate` 가
`history.state.mt` 를 보고 그 깊이까지 닫는다.

- 장점: 오버레이를 하나 더 붙일 때 `openOverlay(이름, 닫는함수, 박스)` 한 줄이면 끝난다.
  포커스 가둠·복귀도 같은 자리에서 처리된다
- 단점: 스택과 히스토리가 어긋나면 진단이 어렵다

## 고민 과정

핵심은 **「한 칸 되감았다」가 아니라 「몇 번째 칸에 도착했다」를 알아야 한다**는 점이었다.
전자로 짜면 `history.go(-2)` (겹쳐 뜬 둘을 한 번에 닫는 경우)에서 하나만 닫히고 하나가 남는다.
깊이를 state 에 적어 두면 몇 칸을 되감든 도착 지점만 보면 되므로 그 문제가 사라진다.

`pushState` 가 막히는 환경(일부 `file://`)에서는 그 오버레이만 히스토리 없이 뜨게 두었다 —
기능이 죽는 것보다 뒤로가기 하나를 포기하는 게 낫다.

## 결정

**옵션 C** 채택.

채택 이유: 오버레이가 넷(앞으로 더 늘 수 있다)인데 분기를 늘리는 대신 규칙을 하나로 만든다.
포커스 관리라는 별개 문제도 같은 자리에서 함께 풀린다.

## 영향

- `app.js` 에 `openOverlay` / `dismissOverlay` / `popOverlaysTo` / `trapTab`
- `closePicker` · `closeNote` · `closeShare` · `closeAllNotes` 는 **감추기 함수가 아니라
  스택에 요청하는 함수**가 됐다. 실제로 감추는 것은 `hide*` 쪽이고, 밖에서 부르면 안 된다
- 모달에는 `aria-modal` 이 붙고 포커스가 갇히며, 닫을 때 열기 전 자리로 돌아간다
- 「전체 메모」는 모달이 아니라 화면이라 포커스를 가두지 않는다 (`box` 를 주지 않는다)
- 스모크 테스트가 겹쳐 뜬 상태의 뒤로가기 순서를 확인한다
